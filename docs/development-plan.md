# План разработки

Документ фиксирует последовательность этапов. Каждый спринт завершается
проверяемым результатом; переход к следующему этапу возможен только после
выполнения критериев выхода.

Текущее состояние: **Sprint 1 — пользователи, аутентификация и RBAC — завершён.**

## Sprint 0 — Technical foundation (завершён)

**Результат**

- структура монорепозитория `frontend/`, `backend/`, `infrastructure/`, `docs/`;
- React 19 + TypeScript + Vite, тёмная дизайн-система на CSS-переменных;
- FastAPI с версионированным API, CORS, единым форматом ошибок;
- `/api/v1/health`, `/api/v1/ready`, `/api/v1/info`;
- async-подключение SQLAlchemy 2 к PostgreSQL (asyncpg);
- `docker-compose.yml` с PostgreSQL 17, томом и healthcheck;
- `.env.example`, `.gitignore`, Git-репозиторий;
- документация: README, architecture, database, api, development-plan;
- unit-тесты и integration-тесты readiness.

**История:** изначально Docker Desktop отсутствовал, поэтому проверки контейнера
были отложены. В рамках Sprint 1 Docker установлен, PostgreSQL 17.12 запущен и
все integration-тесты выполнены на реальной базе. Ограничение Sprint 0 снято.

## Sprint 1 — Пользователи, аутентификация и RBAC (завершён)

**Цель:** полноценная базовая система пользователей — фундамент для остальных
модулей платформы.

### Результат

**База данных и миграции**

- Alembic на async-движке, DSN из настроек приложения;
- ревизия `0001_users_rbac`: `users`, `roles`, `permissions`, `user_roles`,
  `role_permissions`, индексы и внешние ключи;
- ревизия `0002_seed_rbac`: 7 системных ролей, 15 разрешений и матрица
  `role_permissions` (идемпотентно, без удаления данных);
- `create_all()` в рабочем приложении не используется;
- тест отсутствия drift между ORM-моделями и фактической схемой.

**Пользователи**

- модель `User`: UUID, уникальный нормализованный email, Argon2id-хеш,
  отображаемое имя, активность, `created_at`/`updated_at`; лишних полей нет;
- Argon2id с параметрами RFC 9106 (`time_cost=3`, `memory_cost=65536`,
  `parallelism=4`);
- политика паролей (длина, сложность, deny-list, запрет совпадения с email);
- повторная регистрация отклоняется `409`, email сравнивается без учёта регистра;
- хеш пароля не возвращается ни одним эндпоинтом.

**Аутентификация**

- регистрация с авто-входом и назначением только роли `user`;
- вход по email/паролю с проверкой активности аккаунта;
- JWT HS256, секрет только из `.env` (валидация длины и placeholder),
  ограниченное время жизни, проверка подписи, `exp`, `iss` и типа токена;
- `POST /auth/logout` (204) и клиентское удаление токена;
- `GET /auth/me` и `GET /auth/me/permissions`;
- документированное ограничение: серверный отзыв JWT и refresh-токены не
  реализованы.

**RBAC**

- роли и разрешения в реляционных таблицах, несколько ролей на пользователя;
- переиспользуемые зависимости `get_current_user`, `require_roles` (any-of),
  `require_permissions` (all-of);
- профиль защищён `profile:read` / `profile:update`;
- невозможность передать роли, права или `is_active` через регистрацию/профиль
  (Pydantic `extra="forbid"`);
- публичного API назначения ролей нет.

**Личный профиль**

- `GET /users/me` — email, имя, роли, разрешения, дата регистрации;
- `PATCH /users/me` — изменение только отображаемого имени;
- UUID, email, роли и статус изменить нельзя.

**Frontend**

- React Router: `/`, `/login`, `/register`, `/profile`, `*`;
- тёмная палитра обновлена под ориентиры Sprint 1
  (`#101116`, `#191B24`, `#222532`, `#8067F7`, `#38B889`, `#E7A64A`);
- формы входа/регистрации с клиентской валидацией, состояниями загрузки и
  понятными русскими ошибками;
- авто-вход после регистрации, редирект в профиль после входа;
- защищённый маршрут `/profile` с редиректом на `/login`;
- сохранение сессии в `localStorage` с проверкой срока и `GET /auth/me` при
  перезагрузке;
- кнопка выхода в шапке и в профиле; пароли не логируются.

**Тесты**

- 6 unit-тестов (health, info, ошибки, readiness-конфигурация);
- 55 integration-тестов на реальном PostgreSQL (отдельная БД
  `education_platform_test`, миграции Alembic, очистка между тестами);
- покрыты: регистрация, дубликаты, невалидный email, слабые пароли, вход,
  неверный пароль, неактивный пользователь, профиль без токена, истёкший и
  повреждённый токен, изменение имени, запрет лишних полей, невозможность
  назначить роль, недоступность чужих данных, зависимости ролей/разрешений,
  матрица RBAC, отсутствие утечки хеша, соответствие схемы миграциям;
- frontend: `npm run typecheck`, `npm run build`, сквозной сценарий проверен в
  браузере (регистрация → профиль → изменение имени → перезагрузка → выход →
  защита маршрута → вход → ошибка неверного пароля).

**Критерии выхода (выполнены):** регистрация → вход → защищённый эндпоинт
работает на реальной PostgreSQL; роли назначаются только сервером; тесты 401/403
зелёные; секреты только в окружении; миграции применяются на чистой базе;
документация обновлена.

## Sprint 2 — Каталог курсов

**Цель:** публичный каталог и карточки курсов.

- Модели `Course`, `Category`, `CourseModule`, `Lesson`; миграции.
- Эндпоинты каталога: список с фильтрами, пагинацией, поиском; карточка курса.
- Frontend: страница каталога, карточка курса, состояния загрузки/ошибок.
- Права просмотра — `courses:read` (уже засеяно).

**Критерии выхода:** каталог отдаёт данные из БД, фильтры и пагинация покрыты
тестами, frontend отображает реальные данные.

## Sprint 3 — Конструктор курсов

**Цель:** создание и редактирование курсов авторами.

- CRUD курсов, модулей, уроков; порядок элементов.
- Черновик/публикация, валидация структуры.
- Права: автор редактирует только свои курсы, администратор — все.
- Frontend: редактор структуры курса.

**Критерии выхода:** автор создаёт курс с модулями и уроками, публикует его,
курс появляется в каталоге; покрытие тестами прав доступа.

## Sprint 4 — Процесс обучения

**Цель:** запись на курс и прохождение уроков.

- Модели `Enrollment`, `LessonProgress`, `CourseProgress`.
- Эндпоинты записи, старта, отметки урока пройденным, прогресса.
- Правила доступа к урокам, расчёт прогресса.
- Frontend: страница прохождения курса, индикатор прогресса.

**Критерии выхода:** пользователь записывается и проходит курс, прогресс
сохраняется и восстанавливается после перезапуска.

## Sprint 5 — Тестирование и практические задания

**Цель:** проверка знаний внутри курса.

- Модели `Quiz`, `Question`, `AnswerOption`, `QuizAttempt`, `Answer`.
- Типы вопросов (одиночный/множественный выбор, текстовый ответ), проходной балл.
- Проверка ответов, ограничения попыток, результаты.
- Практические задания с ручной проверкой (задел).
- Frontend: прохождение теста и экран результата.

**Критерии выхода:** тест проходится, результат считается на сервере, попытки
ограничены, тесты на граничные случаи.

## Sprint 6 — Сертификация

**Цель:** выдача сертификатов по завершении курса.

- Модели `Certificate`, шаблоны, номер сертификата.
- Условия выдачи (курс завершён, тесты сданы).
- Публичная страница проверки сертификата по номеру.
- Генерация PDF.

**Критерии выхода:** сертификат выдаётся один раз, проверяется по номеру,
содержимое корректно.

## Sprint 7 — Корпоративный кабинет

**Цель:** управление обучением сотрудников.

- Модели `Organization`, `OrganizationMember`, групповые назначения курсов.
- Отчёты по сотрудникам и группам, выгрузка.
- Права организационного руководителя (`organization:*`).

**Критерии выхода:** организация назначает курсы сотрудникам, отчёты совпадают
с фактическим прогрессом.

## Sprint 8 — Административная панель

**Цель:** операционное управление платформой.

- Управление пользователями, ролями, курсами, категориями.
- Назначение и снятие ролей (внутренний API + интерфейс).
- Модерация публикаций, блокировки.
- Журнал действий администраторов.
- Frontend: панель с таблицами, фильтрами, формами.

**Критерии выхода:** ключевые операции доступны из интерфейса, все действия
логируются, права проверяются на сервере.

## Sprint 9 — Уведомления и фоновые задачи

**Цель:** асинхронная обработка и коммуникации.

- Redis + Celery (или APScheduler для периодических задач) — только на этом этапе.
- Очередь email-уведомлений, retry, dead-letter.
- Планировщик: напоминания, пересчёт прогресса, истечение сертификатов.
- Шаблоны писем, настройки уведомлений пользователя.

**Критерии выхода:** задачи выполняются воркером, повторяются при сбоях,
есть мониторинг очереди.

## Сквозные требования

- Каждый спринт: миграции, тесты, обновление `docs/`, осмысленный коммит.
- Секреты только в `.env`; API не раскрывает параметры подключения.
- Границы модулей не нарушаются: доменная логика в `modules/`, транспорт в `api/`.
- Frontend не дублирует бизнес-правила — только отображает и валидирует ввод.
