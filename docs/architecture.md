# Архитектура

## 1. Общая модель

Проект строится как **модульный монолит**.

Один репозиторий, один backend-процесс, одна база данных. Внутри backend код
делится на изолированные доменные модули, каждый из которых будет владеть своей
моделью данных, сервисами и HTTP-роутами. Модули общаются через явные
Python-интерфейсы, а не через прямые запросы к чужим таблицам.

Такой подход выбран осознанно:

- на старте нет распределённых транзакций, сети и дублирования моделей;
- отдельные модули можно позже вынести в отдельные сервисы без переписывания;
- одна команда может разрабатывать проект без инфраструктурных накладных расходов.

Микросервисы, Redis и Celery на Sprint 0 не вводятся — это преждевременное
усложнение.

## 2. Слои

```
┌──────────────────────────────────────────────┐
│ Browser: React + TypeScript + Vite           │
│  app/ (страницы) → components/ → hooks/      │
│  services/ (apiClient) → types/ (контракты)  │
└───────────────────────┬──────────────────────┘
                        │ HTTP/JSON, CORS
┌───────────────────────▼──────────────────────┐
│ FastAPI (backend/app)                        │
│  api/v1/     — HTTP-слой: роуты, схемы       │
│  modules/    — доменная логика (пока пусто)  │
│  core/       — config, database, errors      │
│  workers/    — фоновые задачи (пока пусто)   │
└───────────────────────┬──────────────────────┘
                        │ SQLAlchemy 2 async + asyncpg
┌───────────────────────▼──────────────────────┐
│ PostgreSQL 17 (Docker Compose, volume)       │
└──────────────────────────────────────────────┘
```

Правила зависимостей:

- `api/` знает про `modules/` и `core/`, но не наоборот;
- `modules/` используют `core/` (сессии БД, настройки) и не зависят от `api/`;
- `core/` не импортирует ничего из `api/` или `modules/`;
- фронтенд обращается к backend только через `src/services/`, компоненты не
  вызывают `fetch` напрямую.

## 3. Backend

| Компонент | Ответственность |
| --- | --- |
| `app/main.py` | фабрика `create_app()`, lifespan, CORS, регистрация роутеров и обработчиков ошибок |
| `app/core/config.py` | типизированные настройки из `.env`, сборка DSN, парсинг CORS |
| `app/core/database.py` | async-движок, фабрика сессий, `get_session`, `ping_database` |
| `app/core/errors.py` | единый конверт ошибок, обработчики исключений |
| `app/api/v1/router.py` | сборка версионированного API |
| `app/api/v1/endpoints/*` | HTTP-эндпоинты |
| `app/api/v1/schemas.py` | Pydantic-схемы ответов |

Версионирование: все эндпоинты живут под `/api/v1`. При несовместимых изменениях
появляется `/api/v2`, старый префикс сохраняется на период миграции.

### Обработка ошибок

Все ошибки возвращаются в едином формате:

```json
{ "error": { "code": "not_found", "message": "Not Found", "details": null } }
```

- `StarletteHTTPException` → код из маппинга (`not_found`, `method_not_allowed`, ...);
- `RequestValidationError` → `422`, `code: "validation_error"`, список полей в `details`;
- непойманное исключение → `500`, `code: "internal_error"`, трассировка пишется
  только в серверный лог.

Никакие DSN, хосты, пользователи и пароли в ответы не попадают.

### Liveness и readiness

- `/health` — «процесс жив»; не касается базы, поэтому остаётся `200` при упавшей БД.
- `/ready` — «можно принимать трафик»; выполняет реальный `SELECT 1` с таймаутом и
  возвращает `503` при недоступности PostgreSQL.

Разделение позволяет отличать сломанный процесс от сломанной зависимости и позже
подключить эти эндпоинты к оркестратору.

## 4. Frontend

| Каталог | Назначение |
| --- | --- |
| `src/app/` | корневой компонент `App`, композиция страницы |
| `src/components/` | переиспользуемые UI-компоненты (`ConnectionStatus`) |
| `src/hooks/` | состояние и побочные эффекты (`useBackendStatus`) |
| `src/services/` | транспорт: `apiClient` (fetch, таймауты, ошибки), `systemService` (типизированные вызовы) |
| `src/types/` | контракты API, зеркало backend-схем |
| `src/styles/` | `variables.css` — CSS-переменные тёмной дизайн-системы, `global.css` — база |
| `src/modules/` | доменные модули будущих спринтов |
| `src/assets/` | статические ресурсы |

Дизайн-система начинается с CSS-переменных (`--color-*`, `--space-*`, `--text-*`,
`--radius-*`) в `src/styles/variables.css`. Компоненты используют только токены,
без «магических» цветов и отступов.

Работа с сетью:

- базовый URL берётся из `VITE_API_BASE_URL`;
- каждый запрос ограничен таймаутом (`AbortController`);
- ошибки нормализуются в `ApiError` с типом (`network`, `timeout`, `http`,
  `invalid_response`) и HTTP-кодом;
- UI различает три состояния: «проверка выполняется», «backend доступен»,
  «backend недоступен», и дополнительно показывает состояние PostgreSQL из `/ready`.

## 5. Данные

На Sprint 0 доменных таблиц нет. Подключение к PostgreSQL полностью подготовлено:
движок, пул, фабрика сессий и проверка доступности. Подробности —
[`database.md`](database.md).

## 6. Инфраструктура

- только PostgreSQL в Docker (`docker-compose.yml` в корне);
- backend и frontend запускаются локально, что ускоряет цикл разработки;
- данные БД — в именованном томе, что переживает перезапуск контейнера;
- секреты — только через `.env`, который не попадает в Git.

## 7. Что осознанно не сделано в Sprint 0

Аутентификация, пользователи, курсы, конструктор курсов, обучение, тесты,
сертификаты, корпоративный кабинет, админ-панель, уведомления, Redis, Celery,
APScheduler, Alembic-миграции. Проект не содержит бизнес-логики обучения.

## 8. Направление развития

1. Alembic и первые доменные модели.
2. Пользователи, роли, аутентификация и авторизация.
3. Каталог и конструктор курсов.
4. Процесс обучения и прогресс.
5. Тестирование и практические задания.
6. Сертификация.
7. Корпоративный кабинет и админ-панель.
8. Уведомления, затем фоновые задачи (Redis + Celery / APScheduler).

Последовательность и критерии выхода по этапам — в
